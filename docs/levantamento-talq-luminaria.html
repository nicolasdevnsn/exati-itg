Integração EXATI — Parametrização de dispositivos

Precisamos declarar ao CMS da EXATI, de forma definitiva, quais funções, atributos e eventos o nosso equipamento suporta. Quem conhece o produto é você — este formulário transforma esse conhecimento na declaração técnica.

Marque apenas o que o equipamento entrega hoje. Ao final, gere o resumo e devolva para a equipe de integração.

Por que o "hoje" importa tanto: pela especificação TALQ, uma classe de dispositivo pode ganhar atributos depois, mas nunca perder. Remover algo declarado exige criar uma classe nova e remigrar os dispositivos. Declarar a mais "por garantia" é o erro caro; declarar de menos se corrige em minutos.
O formulário produz duas declarações diferentes. As seções marcadas Device Class descrevem o modelo do equipamento. A seção marcada Serviços é outra coisa: são as capacidades do gateway como um todo, enviadas numa requisição separada. Estão juntas aqui só porque dependem do mesmo conhecimento.
Sobre os termos usados aqui: o equipamento levantado é o ZENIX (SIP) — na TALQ ele faz o papel de controlador do ponto de iluminação (OLC). "Luminária" aparece só quando o assunto é a lâmpada física que ele acende, apaga ou dimeriza. E "gateway" significa sempre o gateway TALQ — o software de integração da Nansen com o CMS da EXATI — e nunca o produto Gateway G1/G2 (DCU / concentrador / access point).
Novidade desta versão — o que a bateria de testes da EXATI nos ensinou: o certificador testa a leitura sob demanda função por função e, para manter os testes verdes, a classe de homologação hoje declara dez funções — quatro delas (sensor de temperatura, nível de bateria, sensor de localização e orientação) entraram por exigência dos testes, sem confirmação de que o ZENIX real as suporta. Elas agora aparecem neste formulário: marque-as apenas se existirem de fato. O que você declarar aqui vira o contrato de produção — cada função declarada terá seus atributos lidos sob demanda pelo CMS. Os itens com selo CERTIFICADOR recebem uma verificação extra: o certificador lê o valor configurado e compara com o estado corrente.

1. Quem está preenchendo

Para sabermos a quem voltar em caso de dúvida sobre uma escolha.

Device Class POST /device-classes → name

2. Identificação da classe

Uma classe descreve um modelo de equipamento. Todos os dispositivos (ZENIX) daquele modelo apontam para ela pelo nome informado aqui.

O cadastro dos dispositivos em si não está neste formulário. Ele acontece em POST /devices, alimentado pela base da plataforma AMI — cada ZENIX só carrega endereço, nome e o nome desta classe. Tudo que descreve o que ela sabe fazer vem daqui.
Device Class POST /device-classes → functions[ ].attributes[ ] · events[ ] · vendorAttributes[ ]

3. Funções, atributos e eventos

Abra cada função e marque o que o equipamento suporta. Os itens com selo OBRIG 🔒 já vêm marcados e travados: são exigidos pelo perfil lighting e vêm com a descrição e o detalhamento abertos. O selo DETALHE indica sub-informação a preencher, que aparece ao marcar. Use o botão i para ler o que cada item significa.

A obrigatoriedade é condicional. No perfil lighting, nenhuma função é obrigatória por si só — todas as quatorze são opcionais para o gateway. O que os itens travados significam é: se você declarar esta função, estes itens dentro dela passam a ser exigidos. Ou seja, a decisão real é sobre a função; os itens vêm no pacote.
Se o equipamento não suportar um item travado, não há como desmarcá-lo aqui — registre na seção de observações qual item é e por quê. A alternativa é não declarar aquela função. Isso é decisão de conformidade, e a equipe de integração precisa avaliar caso a caso com a EXATI.
Serviços POST /services → um objeto por serviço, com seus limites

4. Serviços do gateway e seus limites

Requisição separada da classe, enviada logo depois dela no bootstrap. Serviço declarado é compromisso: o CMS vai usar as rotas correspondentes e respeitar os números informados. Se um limite não for conhecido, deixe em branco em vez de estimar.

Modos de controle que o equipamento executa

Definem, sobretudo, se faz sentido declarar o ControlService. Na operação do dia a dia eles viram POST /calendars e POST /control-programs, mas isso é o CMS que envia ao gateway — não faz parte do que declaramos aqui.

A regra de obrigatoriedade aqui é em duas partes. O agendamento por calendário é obrigatório e vem travado. Além dele, a especificação exige que o gateway suporte pelo menos um dos três modos com gatilho externo — sensor, astronômico, ou astronômico+sensor. Entregar só horário fixo não é conforme.
Nenhum modo com gatilho externo está marcado. A especificação exige pelo menos um entre sensor, astronômico e astronômico+sensor. Se o equipamento realmente não tem nenhum, registre nas observações — é um desvio de conformidade que precisa ser tratado com a EXATI.

Sai em três blocos: o resumo legível, e depois um payload por requisição, já no formato exato do corpo — array, como o protocolo exige. A equipe de integração cola cada bloco na sua rota sem recortar nada.
